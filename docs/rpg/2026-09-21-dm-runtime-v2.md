# 地球之外：大纲、每回合多问题判定与后台改写

> 当前完整机制见 `2026-09-21-dm-logic-v3.md`。用户最新确认采用 Score 基础分布 + 幸运区间调整 + Choice 合法后果，取消无因果的运行时奇遇抽签；本文件保留为历史方案。

日期：2026-09-21。状态：接入前的分工设计；模型接入尚未实现。

后续核心思路审查见 `2026-09-21-core-design-review.md`，包含用户提出的幸运输入、Jev 长线判断范围、并行答案一致性与内容缓冲问题。该文是待验证的修正建议，不代表代码已实现。

## 用户已确定的方向

- 游戏先有大纲和能够直接游玩的剧本。玩家从已展示的有限选项中选择。
- 每次玩家选择后，Jev 对同一份状态批量回答多个问题，决定允许范围内的玩家结果、世界反馈与长期影响。
- 需要改写时，小改动用 Astra low，中等改动 medium，主线结构或长期分支用 high。
- 玩家点击后的必要链路可以包含 Jev 裁定，但不能依赖 Astra 临时写下一幕。新内容在后台提前准备。
- 世界规则、已发生事实、人物因果与伏笔需要持续保持一致。

## 1. 分工

| 组件 | 职责 | 权限边界 |
| --- | --- | --- |
| Codex 运行 Astra | 开局建立世界、大纲、人物目标、伏笔与章节；后台改写未来内容 | 生成版本化内容和补丁，不直接改玩家资源与已发生事实 |
| Jev | 每次选择后多问题并行判定，评估结果、世界反应、长线影响和改写范围 | 从给定候选或量表中输出结构化判断；不写新剧本、不自行读取本地文件或执行工具 |
| 本地运行器 | 状态整理、问题组装、骰子、资源结算、约束检查、存档、内容缓冲与任务调度 | 唯一提交游戏状态的组件；检查答案组合是否一致，只发布适用于当前存档的未来内容 |

Codex 是本机运行通道，Astra 是其中负责规划和写作的模型。low / medium / high 指 Astra 的推理档位，不代表即时返回的保证。

问题与候选由 skill 中的规则及 Codex 生成的章节定义；本地运行器在每回合选取适用问题，Jev 回答。不能把 Jev 当成每回合先自由生成一批问题再自己回答的聊天模型。

## 2. 先准备什么

世界包包含：不可随意变更的世界规则；可以版本化调整的大纲；人物目标及知识边界；伏笔台账；可执行章节；事件和奖励惩罚范围。

章节节点包含：可见叙述、可选行动、行动前提、公开的消耗与检定规则、结果候选、世界反应候选、后续节点条件、对人物线及伏笔的依赖。

大纲规定核心矛盾和可能的发展，不强制唯一结局。章节可以条件合流，但必须保留不同入口带来的事实、人物关系和物品差异。

开局准备可以花时间。每一章进入游玩前，已经展示的所有选择及合法结果都应有到本章收束点的有效路线；新支线备好并校验通过后，再进入可见选项。

## 3. 每次选择之后的问题组

本轮以一份冻结的状态快照为依据。常规动作直接确定成功；困难行动的难度、能力与有利不利修正预先确定，本地掷骰给出结果档位，防止看到点数后临时修改难度。Jev 在这个档位允许的后果范围内判断。

| 问题族 | 示例 | 返回形式 |
| --- | --- | --- |
| 行动后果 | 本次部分成功应对应哪个已允许的代价或奖励组合？ | Choice：预备结果 ID + 概率分布 |
| 世界反馈 | 对方忽略、怀疑、追问、报警，哪种反应符合其知识和动机？ | Choice：反应 ID + 概率分布 |
| 人物关系 | 这次行为对已关联人物的信任意味着什么？ | Choice 或 Score：限定变化档位 |
| 伏笔与承诺 | 本次行为是否满足某条已登记伏笔的触发条件？ | Noul；明确硬条件由程序先检查 |
| 长期走向 | 哪些已登记人物线或结局条件受到影响，程度如何？ | 有界 Choice / Noul / Score |
| 现有内容是否仍适用 | 后续节点是否还满足其事实与进入条件？ | Noul；结合程序条件校验 |
| 改写范围 | 无需改写、局部、片段、结构性改写、信息不足？ | Choice，映射到 none / low / medium / high / hold |
| 随机事件适用性 | 当前是否适合出现某个已备好的奇遇？ | Noul 或 Choice，供事件调度规则使用 |

只询问这次行为能影响的对象，不把整个世界的所有问题每回合都发送。首版可从约 6–10 个适用问题起步，遇到依赖关系时增加少量条件问题；实际成本与延迟需要测量后调整。

TypeSafe 接口允许一个 `state` 搭配多个 `questions`。官方说明多个问题并行评估；问题增加仍消耗 token。官方的低延迟描述不是本游戏端到端时延的实测结论。

## 4. 并行问题之间的依赖

同一批问题独立针对输入状态评估，不能假定一个问题已经读到了同批另一个问题的答案。

例如奖励结果有 A、B 两种，而且长线影响取决于哪个结果发生：在同一批里分别评估“若 A 发生，对长线有什么影响”和“若 B 发生，对长线有什么影响”，最后只采用实际结算结果对应的回答。小型条件展开仍能放在一轮请求中。

关系紧密、不能自由组合的后果应合并为合法结果包。例如“成功取走借据且商人没有发现”和“成功取走但商人发现”分别定义候选，避免把独立答案拼成“偷窃失败但凭空得到了借据”。

候选包或条件分支过多时，缩小当前可发布选项的复杂度，或在后台准备更完整的章节；首版不采用没有上限的多轮追问。回答缺失、越界、冲突或适用条件不成立时，本回合不提交，保留原存档并明确提示失败；不得擅自随机拼出结果。

## 5. 概率分三类

1. **规则概率**：骰子成功率、奇遇基础触发率、物品稀有度等由世界规则定义，运行器负责抽样并留存随机结果。
2. **Jev 判断分布**：候选结果与当前上下文有多相符。Choice 默认给出最高概率候选，并不自动按这个分布掷骰；Noul 返回 yes 的概率判断。
3. **模型 confidence**：由分布形状推导的判断确定程度。它不是玩家成功率，也不是剧情正确率。

可以设计“让 Jev 的分布影响世界随机性”，但必须显式列为游戏机制：先排除非法结果，再按预定规则将剩余概率转成权重，由本地运行器抽样；保留基础概率、上下限和冷却。原始模型概率不是经过校准的真实事件频率。

首版建议：行动成败使用预先固定的骰子规则；语义后果优先采用 Jev 的合法判断；低风险奇遇可使用经约束的概率抽样。维持因果一致性或修复已经失效的剧情，不通过抽签决定是否执行。

## 6. 长线影响如何调度 Astra

| 等级 | 适用范围 | 行为 |
| --- | --- | --- |
| none | 现有章节已经覆盖行动后果，相关人物线和进入条件仍有效 | 继续使用现成内容 |
| low | 对白、态度、眼前描写等局部变化，不改变主要依赖 | 后台修改少数未来段落 |
| medium | 人物关系、支线顺序、若干场景的进入方式或伏笔回收路径变化 | 后台修改相关片段 |
| high | 关键人物退出、主要证据消失、阵营变化、结局条件变化、需要长期新分支 | 后台更新受影响的大纲和未来章节 |
| hold | 无法形成一致判断，或候选与已发生事实冲突 | 隔离问题、保留有效状态；只在明确范围内交 Astra high 复核 |

调度依据是因果影响范围，不是动作看起来有多大或文案长度。运行器依据关键依赖设置最低档位，避免把改变结局条件的补丁当作低成本润色。

Jev 每回合仍然被调用。即使判定结果是 none，也完成了对该回合世界反馈和长期影响的评估；不因此强制调用 Astra。

## 7. 两条运行路径

```text
即时路径：玩家选择 → 本地检查 / 必要时掷骰 → Jev 一次批量判定
                                          ↓
                         一致性检查 → 结算 → 现成剧情与新状态

后台路径：                 本轮长线影响
                               ↓
                无需改写 / Astra low / medium / high
                               ↓
                  校验未来补丁 → 更新尚未展示的剧本
```

当前章的可玩储备必须覆盖已发布选择。未来章节在后台补充，缓冲量按玩家连续快速点击还能走多少有效节点计算，不能用故事中消耗的时间估计现实生成窗口。

等待 high 改写时，只有仍符合已发生事实的准备内容可以继续使用。不能为了等待而撤回玩家的选择、播放矛盾的旧剧情或反复灌入无意义的过渡场景。

如果下一章准备不足，在明确的章末承认准备状态，并记录缓冲耗尽。首版目标是本章可完整游玩、平时点击不等待 Astra；有限预算和任意快点击下的无限无等待新剧情不能仅靠这个设计保证。

## 8. 版本、伏笔与发布

- 已发生事实及已展示内容不可被后台改写。未来补丁绑定生成时的状态版本与前置条件；返回时再次检查，过时结果不能覆盖新进度。
- 数值、物品与能力由运行器统一结算；Jev 和 Astra 只能提出允许范围内的结果 ID 或补丁。
- 伏笔记录埋设依据、相关人物线、触发条件、允许回收方式、已实现或错失状态。改写必须同步更新这些依赖，不能无声丢弃承诺。
- 角色秘密、世界真相与未来选项留在主持服务端，前端只拿玩家已知内容。凭据不进入页面、世界包或存档。
- 合并尚未执行的相关后台任务；过时任务可以放弃发布，但已发出的请求仍计入成本，不能用自动重试掩盖失败。
- 程序可检查资源、条件、引用、节点可达和版本；语义、人物动机及长篇叙事质量还需要复核和试玩。

仅完成现有代码、Codex CLI 登录和 Jev models 鉴权检查；尚未发出游戏生成或 Jev Choice 请求，也未改变当前 HTML 示例。早先“每回合等待 Codex 生成”的方案已标为废弃。

实现顺序：先定义可执行章节与问题契约，再做本地状态结算与缓冲，随后接入 Jev 批量裁定，最后接入 Astra 分档后台改写。真实验证仍遵守本轮事先声明的 3 次 Codex 生成、2 次 Jev 判定上限；没有自动重试。

验收分别测量点击到结果的 p50 / p95 / 最大值、Jev 一批问题的实际耗时、Astra 各档耗时、模型等待回合数、缓冲耗尽、重复提交、断线恢复、过时补丁、资源重复扣减和事实冲突。少量真实请求只能确认链路，不能作为长期稳定性或 p95 证据。

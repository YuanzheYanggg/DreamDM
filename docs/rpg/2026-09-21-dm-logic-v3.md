# 地球之外：有限篇幅 RPG 的完整主持逻辑 v3

日期：2026-09-21。状态：完整设计规范；2026-09-22 已实现六场景接入试验，验证状态见 ../../rpg-prototype/QA.md；长篇与动态剧情图尚未实现。依据用户最新七点要求整合，数值默认值均为待试玩调整的建议。

2026-09-22 试运行补充：整局配额已实现为 Jev 130 / Astra 18。开局不确定项采用主导演证据复核，回合加入具体冲突分类，三个未改动固定终局采用有审批和本局事件依据的执行契约；具体门槛与真实限制见 [当前 QA](../../rpg-prototype/QA.md)。这是六场景实现的试运行策略，不代表长篇正确率已验证。

本规范替代 v2 中“规则先确定成败、Jev 只选后果”的建议：现在由 Jev Score 形成基础结果分布，运行器只用一次本次幸运与角色幸运属性确定档位，再使用 Jev Choice 的条件答案确定具体后果。取消游玩时无原因的随机奇遇抽签；奇异性主要来自 Astra 创作，事件按条件触发。

## 1. 产品与世界约定

- 一局目标 20–30 分钟，约 100 次推进剧情的选择；查看背包、展开记录等界面操作不占剧情回合。
- 可在目标轮数之前自然结束，不为凑数重复场景。首版以 100 个剧情回合作为内容预算；最后阶段保留收束容量。
- 世界年代、奇幻规律、核心冲突和已经发生的真实历史保持稳定。人物走向、阵营、解决路线、幸存者和结局可以改变。
- Astra 是总导演和编剧；Jev 是按已知事实与允许范围裁定的 DM；本地运行器管理真实状态、幸运结算、内容发布和任务调度。
- 普通动作无需额外的成败随机。每回合仍可调用 Jev 判断语义反馈、人物反应与后续影响；不意味着每回合必须使用所有三种原语。
- 惊喜来自合理的新信息、伏笔兑现、人物动机和前期选择的后果。Jev 不为了好玩擅自投放无因果的事件。

## 2. 开局前 Astra 需要产出什么

按顺序生成并校验：

1. 世界约定：规则、边界、年代、主角身份、核心冲突、风格、时长和结尾需要回答的问题。
2. 真相与人物关系：先写发生了什么，再写各人知道什么、相信什么、想要什么、愿意付出什么。
3. 可变化大纲：阶段目标、几条可能的解决路线、事件前提、结局条件与不可静默破坏的承诺。
4. 伏笔与线索表：埋设节点、不同获取途径、可回收条件、对应结果、可否错过。
5. 可执行章节：节点、选项、前提、消耗、局部目标、结果档位、完整后果包、后续节点、人物知情范围。
6. 内容储备：整局有一套可走到结尾的基础内容；靠近当前回合的内容更细致。后台改写尚未展示的变体。

基础内容可以复用有条件节点，不要求穷举所有 100 步历史。任何已发布选项的合法结果，都要有与结果状态相容的有效后续路线；不能因为后台未完成就取消该选项的承诺。

每个选项提前声明自己的局部目标。例如“打开档案馆侧门”与“无声进入档案馆”是不同目标，不能拿同一套好中坏标准混用。

## 3. 三种 Jev 原语各司其职

### 3.1 Score：有顺序的程度与结果分布

首要用途是 `outcome_quality`，三个完整描述的等级按坏、中、好排列：

- 坏：未实现本次声明的目标，承担已提示范围内的代价；存在后续可行路线。
- 中：部分实现目标，或者达成目标但承担事先允许的额外代价。
- 好：实现本次目标，代价在正常范围内，允许获得与因果相符的额外便利。

实际 criteria 要写成该行动的具体情境，不能只填“坏、中、好”。也不能把好等同于道德高尚或最终人生幸福。一个成功揭示悲惨真相的动作，仍可能是信息获取意义上的好结果。

官方 Score 返回各等级的 `probabilities`、加权均值 `score`、`legend` 与 `confidence`。三档编号为 0、1、2；运行器采用完整分布，不把均值四舍五入当成实际结果。同为 score=1，可能是中 100%，也可能是坏 50% / 好 50%。[Score 接口](https://docs.typesafe.ai/primitives/score)

其他 Score 问题可以分别衡量：

| 问题 | 示例等级描述 | 用途 |
| --- | --- | --- |
| 紧张程度 | 有余裕 / 需要权衡 / 时间与资源都紧张 | 安排后续场景强度 |
| 当前目标关联度 | 无直接关联 / 补充人物或线索 / 直接推进当前冲突 | 判断是否需要提示目标，而非强拉回固定路线 |
| 长期影响范围 | 无持续影响 / 人物或支线影响 / 多条因果依赖改变 | 辅助改写范围判断 |
| 收束准备程度 | 关键因果仍未知 / 已知冲突等待决定 / 可展示决定后的后果 | 判断尾声是否有充分依据 |

每个 Score 保持一个维度。人物关系、剧情紧张程度和资源压力分别判断，不能混成一个含义不清的总分。

模型分布在本游戏中被显式约定为“候选结果的基础裁定权重”，不是已校准的现实成功频率。模型、问题模板、世界包和规则版本一起记账；通过固定案例检查其是否符合设计预期。

### 3.2 Noul：条件是否成立、是否存在问题

适用问题：候选后果是否违背某条世界法则；是否与既定历史冲突；某 NPC 的反应是否使用了他不知道的信息；这项承诺是否已经满足；某伏笔是否到了可回收条件；一条未来路线的前提是否受到破坏。

一个问题只判断一件事。Noul 返回命题为真的概率判断，不把 0.8 理解成“80% 的伏笔被完成”，也不按 80% 抽签触发。官方说明中间值表示不确定，而非程度中等。[Noul 接口](https://docs.typesafe.ai/primitives/noul)

采用 yes / no / unknown 三态。可以从 yes≥0.85、no≤0.15 的示例阈值开始，但矛盾检查、台词选择等不同风险采用不同策略；这些阈值尚未经本游戏校准。

明确字段条件直接由程序判断，例如钥匙是否在背包、角色是否死亡。Noul 用于需要语义理解的条件，不重新猜已经确定的数据库事实。未知也不能成为凭空改变事实的许可。

### 3.3 Choice：从合法候选中做出明确决定

适用问题：如果本次结果为某档，哪一个完整后果包最合适；某 NPC 按自己所知如何回应；接下来哪个已准备场景最能承接事实；需要何种改写任务。

Choice 返回候选 ID 及分布，默认选择最高概率候选；此处不再次按分布随机抽样。候选相同优先级时按版本化稳定顺序处理，避免增加隐藏随机源。[Choice 接口](https://docs.typesafe.ai/primitives/choice)

每个候选包同时包含叙述、资源变化、获得或失去的物品、产生的事实、谁看见什么、关系变化、后续节点及长期依赖。不能把互相约束的事实交给若干独立选择后随便拼接。

## 4. 概率与幸运：只做一次档位判定

### 4.1 基础分布

玩家选定行动，运行器冻结本轮状态。Jev 根据世界约定、相关历史、行动目标、能力、道具、环境和当前资源形成：

```text
P_base = [p_bad, p_mixed, p_good]
p_bad + p_mixed + p_good = 1
```

先屏蔽不可能或没有合法候选的档位，再对剩余有效权重归一化。格式错误、负数、缺键、全零和明显不归一等回答视为失败；只纠正允许误差内的浮点舍入，不修饰错误数据。

没有合法承接内容的选项不得发布。普通且条件满足的行动可由规则固定分布为 [0,0,1]，无需 Score 对其成败重新裁定。

### 4.2 一次幸运落点

建议首版数值，允许世界包调整但开局后固定版本：

```text
L = 角色幸运属性，0..100，50 为中性
F = 本次幸运点，均匀取值 [0,100)，每个行动只生成一次并保存
Δ = clamp(0.2 × (L − 50), −10, +10)
Q = clamp(F + Δ, 0, 小于 100 的最大可表示值)

坏区间：[0, 100×p_bad)
中区间：[100×p_bad, 100×(p_bad+p_mixed))
好区间：[100×(p_bad+p_mixed), 100)
```

Q 落入哪个区间，最终就是哪个档位。这等价于向有利方向移动判定边界；不同时再移动概率和落点，否则会重复加幸运。

实现用 10,000 个整数基点避免区间边界含混：分布用最大余数法转换成总和恰好 10,000 的权重，F 取 0..9999，Δ 转成整数基点，Q 夹在 0..9999。最大余数平局采用固定等级顺序。概率为零的档位区间宽度为零，不能被幸运凭空选中。

本次幸运 F 已经是唯一随机落点，不能再另掷一枚骰子选好中坏。后果 Choice、伏笔 Noul、尾声选择不再随机抽样。

### 4.3 一个具体例子

```text
基础分布：坏35% / 中45% / 好20%
基础区间：坏[0,35) / 中[35,80) / 好[80,100)
L=75 → Δ=+5
F=78 → Q=83 → 好
```

没有幸运属性修正时本次是中，修正后进入好。长期看，在这个例子里实际分布变成坏30% / 中45% / 好25%，合计仍为100%。L=25 时则为坏40% / 中45% / 好15%。

存档分别记录模型基础分布、屏蔽与归一化后的分布、幸运修正后的实际分布、F、L、Δ、Q、最终档位和具体后果。不能用基础概率冒充加幸运后的实际概率。

实际概率按映射后落点的频数或精确区间计算；零宽区间、仅有一档和上下边界都需要正确处理。

### 4.4 幸运输入与公正性

完整回合判定数据包含 L 与 F；基础概率请求采用不包含这两个实际数值的投影，防止 Jev 先受幸运影响，随后运行器又加一次。提交后的完整判定单可成为后续 Jev/Astra 的历史输入。

完整状态存在并不意味着每个问题都必须收到所有字段。概率判断、NPC 反应和后台导演各有自己的输入视图。

基础概率视图也不输入纯粹的导演压力，例如“已经第90轮，必须让玩家赢”或“刚成功三次，下一次需要受挫”。只有真正改变当前环境的已提交事实才影响本次机会；回合预算、连胜连败和收束需求交给导演视图决定未来内容。

F 在发起请求前登记，不给基础 Score 看；断线、手动重试和刷新都复用同一行动的 F。第一次有效分布和答案保存后不再重新判定同一行动。未得到有效答案前不扣资源、不推进时间和剧情回合。

幸运只能提高当前可实现结果的档位，不能让死者复活、让不存在的证据出现、绕过玩家未接受的永久代价。结局中的价值抉择由玩家决定，不能被幸运改成系统认为更好的道德选择。

## 5. 一轮批量请求如何处理依赖

同批问题相互独立，不能把同批 Score 的尚未返回结果当成另一个 Choice 已知的条件。[并行和依赖规则](https://docs.typesafe.ai/primitives)

对选定行动提前构造：

- Score：基础结果分布。
- Choice：如果结果为坏，选择哪一包后果。
- Choice：如果结果为中，选择哪一包后果。
- Choice：如果结果为好，选择哪一包后果。
- Noul：针对具体候选的冲突、承诺、伏笔与前提问题。
- Choice / Score：若某候选生效，它影响哪些已登记依赖，何种改写适用。

运行器得到全部答案后才计算幸运档位，取出该档 Choice，以及该候选对应的条件答案。其他回答不修改世界。基础字段已确定的条件由程序计算，减少无意义问题。

首版每个档位通常只放1–2个完整候选。只询问当前行动影响的实体，避免把全世界的组合笛卡尔积放进一轮请求。数量预算是产品调度参数，不是 API 固有限制；实际耗时与成本再测。

### 知识域与并发边界

同一请求的所有问题都会看到同一份 state。如果真的要隔离秘密，不能把完整主持秘密放进 state 再仅写一句“请 NPC 忽略”。

- 主持判断使用相关的世界真相、依赖和已提交事实。
- NPC 反应使用该 NPC 的记忆、观察、目标和可见候选，不含他未知的真相。
- 玩家页面只拿已经公开的叙述、状态和线索。

因此同一个回合可以包含按知识域分开的并发批次。通常一个主判定批次；需要独立 NPC 判断时加入对应批次，而不是为了机械追求一个 HTTP 请求泄露知识。条件候选已确定时，各批次可以同时评估；遇到真正需要先取回新数据的依赖，不伪装成独立并行。

若独立 NPC 答案与主持候选有关，问题必须提前以候选 ID 为条件。运行器只接受发布时定义的兼容组合；未定义组合不由任意一方的高置信度强行覆盖另一方。单个回合涉及过多角色或条件时，在内容设计阶段拆成连续的短节点，而不无限增加在线判定层数。

## 6. Astra 编写、Jev 预检、运行器发布

新内容的流程：

```text
Astra 生成草稿与全部允许后果
    → 程序检查字段、引用、资源、图结构与前置条件
    → Jev Noul 检查已知历史、人物知识与行为的语义一致性
    → 冲突或未知内容返回修改；记录具体候选与依据
    → 检查各结果有有效的后续及结尾路径
    → 原子发布一个内容版本
```

预检依据状态范围或前置条件签名保存。当前状态离开该范围时不能继续沿用旧检验。模型写得合法加上 Jev 同意，也不能证明没有所有语义漏洞；仍须设计案例和实际试玩。

真正的玩家行动提交时，再检查该候选与最新状态的一致性。相互依赖的资源、事实、知情变化和场景一次提交；不能先发剧情，再补失败的背包操作。

## 7. SQLite / JSON / Markdown 的分工

建议使用 SQLite 保存一局真实状态，JSON 保存可导入导出的世界包与结构化模型协议，Markdown 保存人读的创作设定和解释。运行时只以数据库已提交记录为准，不让 Markdown 和 JSON 各自偷偷成为另一份实时真相。

首版可用少量关联表配 JSON 内容列：

| 表 | 最小关键字段 | 作用 |
| --- | --- | --- |
| world_versions | world_id, version, constitution_json, canon_json, outline_json | 固定世界规则、起始真相、版本化大纲 |
| sessions | session_id, world_version, revision, turn, node_id, actor_state_json, pacing_json | 当前存档；角色能力、幸运、资源与物品可先放 JSON |
| entities | session_id, entity_id, kind, goals_json, traits_json | 人物、地点与组织；人物目标的实际状态 |
| facts | session_id, fact_id, subject_id, predicate, value_json, truth, source_event, valid_from, valid_to | 世界命题及真实状态；truth 为 true/false/unknown，事实改变保留历史 |
| beliefs | session_id, holder_id, fact_id, belief, learned_event | 谁知道或相信什么；可以存在与事实不同的错误信念 |
| relations | session_id, from_id, to_id, type, value, source_event | 有方向的人物关系；A 信任 B 不代表 B 信任 A |
| story_nodes | world_version, node_id, node_version, status, content_json, preconditions_json, outcomes_json | 草稿、已审核和已发布场景；每个选项和后果有稳定 ID |
| dependencies | source_kind, source_id, target_kind, target_id, condition_json | 事实、人物、承诺与未来节点之间的有向依赖 |
| hooks | session_id, hook_id, seed_event, state, trigger_json, payoff_node_ids | 伏笔、承诺及回收条件；保留真实埋设依据 |
| events | session_id, event_id, turn, action_id, request_id, before_revision, after_revision, receipt_json | 已提交选择与判定单；request_id 唯一，支持重放和防重复 |
| turn_attempts | session_id, request_id, expected_revision, phase, fortune, answers_json, error | 尚未提交的行动与一次性幸运；失败恢复不能重掷 |
| director_jobs | job_id, session_id, effort, read_set_json, target_nodes, deadline_node, status, patch_json | Astra 后台任务、真实影响范围、适用条件和草稿结果 |

这是表结构设计，不是本轮已创建的数据库。复合外键要把 session/world version 带上，避免不同世界的同名对象串联；细节 JSON 的字段校验由运行器执行。

示例：事实 F17 为“商人把借据交给了林照”；玩家与商人的 beliefs 指向 F17，守卫没有这条记录。若守卫只看见交易但不知道物品内容，应新增对应较弱命题，不直接让他知道 F17。

SQL 表名或 visibility 字段不会自动隔离知识。上下文构建器根据任务身份读取允许的行和字段，产生独立模型输入；前端通过玩家投影接口读取，不能下载完整数据库再靠 CSS 隐藏。

权限方向：Astra 读导演视图、只写待审草稿；Jev 读本次任务投影、只返回答案；运行器检查后独占写入已提交事实；UI 只能提交当前选项 ID 与预期 revision。

## 8. 平衡发展：管理未来节奏，不篡改本次运气

Jev 可以判断近期是否太压抑、缺乏挑战、长时间没有新信息，或者探索已经难以在剩余篇幅中收束。运行器同时给它真实统计，不要求模型凭感觉数输赢。

统计至少包含：近期有风险行动数、幸运调整后各回合的期望档位、实际档位、资源净变化、连续挫败、上次恢复机会、未解决承诺和关键线索进度。

可以用 `实际档位 − 幸运调整后的期望档位` 作为运气偏差的辅助量。不能直接把高能力、高幸运角色的正常成功率当作“运气过好”，也不把主动选择高风险造成的损失全部算作坏运。

节奏调整只影响未来尚未发布内容：连续挫败后提供有来由的休整或合作机会；进展顺利时开放更高价值、风险清楚的挑战；临近尾声时停止扩张新长支线，集中兑现已有关系与承诺。

不要求所有玩家好坏各半，不暗扣高幸运的效果，不因为成功太多就让下一次必败。必要的动态难度规则必须在世界配置中说明，并在相关选项发布前生效。

“偏离主线”分为两个维度：违反世界法则的候选必须拒绝；在世界内探索不同人物和路线属于合法自由，仅结合剩余篇幅安排如何承接和收束。

## 9. 约 100 次选择的节奏与编剧方法

100 次选择用 20–30 分钟完成，平均每次只有12–18秒，包括阅读、思考和 Jev 网络响应。这是时间除法，不是实测阅读速度。若每轮都给长段文本，目标无法同时成立。

初始内容预算可设为约80次短行动/回应、15次重要交流或推理、5次关键抉择。短行动也应提供信息、关系反馈、资源改变或人物表达，不能只是“继续”按钮。

普通节点正文约20–60个汉字、通常2–3个简短选项；重要节点可以更长，以减少其他节点字数平衡。复杂名词、背景设定和长回顾放入可选展开，不在每轮重复。以上是写作起点，最终以试玩时间调整。

| 回合范围 | 叙事职责 | 玩家应获得的体验 |
| --- | --- | --- |
| 1–10 | 给出一个具体异常、主角个人牵挂与可完成的小目标 | 快速入戏，早期选择有可见回应 |
| 11–30 | 建立少量关键人物、目标冲突和线索入口 | 自己发现信息，开始形成关系 |
| 31–55 | 让早先选择改变通行方式、可信对象或调查效率 | 感到世界记得自己，获得第一次明确回报 |
| 56–75 | 揭示有证据支持的反转，让动机或代价重新显现 | 惊讶后能回想起依据，而非被新规则欺骗 |
| 76–90 | 汇聚已知证据和关系，给出具有代价的解决方案 | 玩家作出决定，属性和前期积累派上用场 |
| 91–100 | 展示主要后果、兑现核心承诺、解释仍悬而未决的部分 | 看到选择的分量，获得完整结束感 |

这些是阶段预算；实际进度由信息、人物线和结局条件共同决定，不能只因为 turn=76 就强行反转。Jev 看到 phase、turn、remaining_turns、未解核心问题、需回收承诺、最短结局路径和内容储备；不只给它一个百分比。

玩家阅读更慢不算游戏内时间消耗，也不应惩罚慢读者。若试玩的100次选择超时，优先压缩重复内容或减少目标选择数，不牺牲结尾完整性。

### 从创作者方法中借鉴，如何落实到本游戏

- **人物关系先行。** 猫司图的作者访谈描述从人设、关系和动机织出剧情。这里转成每个关键 NPC 的目标、秘密、底线及与其他人的冲突；即使只服务一个主角，NPC 也有独立动机。[作者访谈](https://www.chinawriter.com.cn/n1/2021/0727/c405057-32170976.html)
- **承诺、进展、兑现。** Sanderson 的写作课以这三者组织读者期待。这里转成开局提出的核心问题、沿途可见的接近、结尾必须回应的事项。[作者课程](https://www.brandonsanderson.com/blogs/blog/brandon-sandersons-2025-guide-to-plot-lecture-2)
- **延迟分支。** Choice of Games 的创作说明使用早期状态影响后期选择，允许章节合流。这里保留关键事件 ID 和少量状态，控制分支规模并兑现历史影响；不能合流后抹掉差异。[创作方法](https://www.choiceofgames.com/2011/07/by-the-numbers-how-to-write-a-long-interactive-novel-that-doesnt-suck/)
- **关键推理有多条线索入口。** Justin Alexander 的 Three Clue Rule 建议为关键结论准备多个线索。这里为必须能推进的结论准备三种独立获取途径，避免一次坏运封死整局；线索不等于直接告诉答案。[原作者文章](https://thealexandrian.net/wordpress/1101/roleplaying-games/three-clue-rule-part-3-the-three-clue-rule)

这些是创作方法与本项目的迁移建议，不是“采用后一定上瘾”的效果证据。我们要争取的体验是好奇心有回应、选择有持续后果、推理有依据、付出有回报、结尾有分量。

## 10. 合流、长期影响与后台改写

合流是“不同经历抵达同一个可复用场景”，不是删除经历。例如大家都来到钟楼，但有的人拿着借据，有的人带着证人，有的人被守卫怀疑；门口的选项、代价和可用解决办法不同。

| 档位 | 改动范围 | 例子 |
| --- | --- | --- |
| none | 现有内容已经覆盖该状态 | 使用既有借据入口 |
| low | 局部措辞或少数未来段落，依赖不变 | NPC 采用更亲近的称呼 |
| medium | 相关人物线、几个节点条件或回收方式改变 | 原合作伙伴拒绝帮忙，另一条证据路线承接 |
| high | 多条因果依赖、主要路线或结局条件改变 | 关键人物退出，需要重排其承担的未来作用 |

Jev 评估已定义条件与语义影响，程序沿依赖表找到具体节点；Astra 负责未建模的复杂新因果。每项任务还要记录最早失效节点、剩余可玩内容和依赖事实，不能只贴一个 high 标签。

当前回合始终使用已准备的合法结果。后台补丁只修改未展示区域；返还时检查相关 read set，仍适用才发布。无关的背包变化不必废弃整项写作，关键人物死亡则必须使依赖其存活的补丁失效。

新重大分支未准备好前不发布其入口；已发布选项的结果必须兑现。准备好的基础路线允许整局结束，后台任务失败时使用仍兼容的已备内容；如果所有已备路线都失效，那是内容发布约束失守，要如实记录并停止推进，不能伪造一个过渡场景掩盖。

## 11. 完整回合的执行顺序

1. 接受当前选项 ID、session 和 expected revision；拒绝旧版本或重复提交。
2. 检查前提与已备结果，冻结状态；对有风险行动登记一次 F，写入 turn_attempts。
3. 组装不含本次幸运的基础概率视图，以及需要的主持/NPC 视图；发起有限的 Jev 并发问题批次。
4. 验证回答结构、条件适用性与矛盾检查。计算基础有效分布，并用 L、F 确定最终档位。
5. 取该档 Choice 的后果包，只采用与这个包对应的条件答案；不能把其他分支的回答提交。
6. 在事务内提交资源、物品、事实、人物知情、关系、伏笔、下一节点、回合数和判定单；唯一 request_id 防止重复结算。
7. 返回玩家投影：现成的故事反馈、状态变化、已知线索和下一组选项。页面不等待 Astra 写作。
8. 根据已提交后果和剩余篇幅合并后台导演任务，选择 none/low/medium/high；预检和发布新版本。

Jev 网络或关键判定失败时保留上一份有效状态与 F；重试必须明确触发，不自动重掷或重复扣资源。仅后台非关键导演判断待补时，可以继续使用已发布、条件仍成立的储备内容。

## 12. 雾港第 37 回合示例

玩家选“用旧铜钥匙打开档案馆侧门”。局部目标是打开门，进入之前的普通检查已确认钥匙持有与精力足够。

- Astra 已准备坏、中、好各自的完整后果与接下来可玩的节点。
- Score 示例分布为35/45/20；Noul 检查既有钥匙来历、机关规律和候选的知识边界；各档 Choice 提前选择最适合该条件的结果。
- 幸运属性75，本次幸运78，偏移后83，进入好档。
- 好档 Choice 选择“钥匙吻合、侧门打开，未留下撬痕”；按已展示规则扣除正常精力，记录通行事实。没有目击者，就不给守卫增加知情记录。
- 下一幕立即使用已准备的档案馆内容。此前是否借出绰号，决定能否认出借名簿上的笔迹；不会无条件送给玩家所有秘密。
- 若现有后续已经覆盖安静进入，改写为 none。若别的合法结果留下撬痕，程序登记痕迹；守卫只有未来真正发现它后才产生相应知识和反应。

示例不是一次实际 Jev 返回；所有数值用于说明协议。

## 13. 验证与交付界限

本轮只核对官方接口、查阅创作者一手方法、完成设计和幸运映射数学检查。没有真实游戏模型请求，没有创建生产数据库，没有声称玩法或延迟已达标。

数学检查枚举了7种基础分布、每种10,000个幸运落点、−5/0/+5三种偏移，共210,000个档位结果；完成140,000次相邻偏移的非降比较。所测情境中，概率质量守恒、零概率档位未出现、增加幸运未降低档位。它证明这些例子中的映射性质，不证明 Jev 概率合理或剧情好玩。

后续验证优先覆盖：

- 相同案例的基础概率是否稳定体现能力、工具和环境；不得把高 confidence 当成正确率。
- 幸运只用一次、有效概率合计100%、普通行为无随机失败、不能选中不可能档位。
- 并行答案能形成一致后果，NPC 不使用未获知事实，主要证据不被坏运唯一封死。
- 一局的实际阅读与选择耗时；网络延迟、错误率和停等次数单独记录。
- 关键选择改变后期通行、人物反应或结局，合流后差异保留；结尾回应开局承诺。
- 慢生成、重试、后台补丁过时和断线恢复；不改旧事实、不重复提交。

可下载 bundle 最终需要 skill 规则、世界包、HTML 与本地运行器。在线 Jev/Codex 调用仍需各玩家自己的可用登录/凭据与额度，不能打包当前机器的认证信息。
